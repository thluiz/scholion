O texto apresenta open source como algo que vai além de abrir o código, porque também depende de licença, permissão para redistribuição, obras derivadas e ausência de discriminação. Em seguida, defende que contribuir pode ajudar no aprendizado, na troca com a comunidade e na construção de portfólio.

## Fichamento

- Contribuir em open source não se limita a escrever código, porque também há espaço para design, documentação, organização, eventos, suporte e curadoria de listas.
- Antes de entrar em um projeto, vale observar licença, atividade recente, volume de issues, forma de resposta dos mantenedores, discussões e histórico de pull requests.
- O texto descreve partes comuns de um projeto open source, como author, owner, mantenedores, contribuintes, comunidade, LICENSE, README, CONTRIBUTING, CODE_OF_CONDUCT, issue tracker, pull requests e chats de discussão.
- Para encontrar projetos, o guia cita buscas no Github e ferramentas como Up For Grabs, Issuehub.io, Code Triage, First Timers Only, YourFirstPR e Github Explore.
- Ao abrir issues ou pull requests, a orientação é dar contexto, mostrar que você pesquisou antes, ser curto e direto, manter a conversa pública, ser paciente e respeitar as decisões do projeto.
- O texto recomenda abrir issues para relatar erros sem solução ou propor ideias, e abrir pull requests para correções pequenas ou para começar uma contribuição já combinada em uma issue.
- Um pull request pode ser aberto cedo, desde que seja marcado como WIP, com branch separado, referência a issues, screenshots quando necessário e testes feitos antes do envio.
- Depois da contribuição, o texto diz que pode haver silêncio, pedido de mudanças, recusa ou aceitação, e orienta responder com educação e continuar procurando outros projetos se necessário.
