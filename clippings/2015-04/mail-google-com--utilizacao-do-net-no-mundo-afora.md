TomamaisThu, Apr 16, 2015 at 3:45 PM

Complicadásso isso,

Do lado da tecnologia, é uma discussão que tenho com alguns colegas. Teve um tempo que novas linguagens e tecnologias figuravam como ferramentas diferentes para resolver o mesmo problema. Hoje o papo é outro.

Você não substitui [ASP.NET](http://asp.net/) com IIS ou Java com JBoss por NodeJS porque quer. Você faz isso porque precisa. Os frameworks e linguagens mais novas vêem para resolver problemas novos. Você não vai mudar seu sistema web para um SPA porque é legal, mas porque precisa, seja por um requisito ou pela natureza da aplicação. MeteorJS e SignalR não devem ser usados se não forem necessários, mesmo sendo "muito legais".

O mesmo vale para metade do que citou, incluindo Scala e GO. Outros que entram na jogada são servidores como Hadoop e BDs como Mongo. Não se usa porque é moda. Eles vieram com a proposta de resolver problemas novos.

Antes que floquinhos venham atacar, sim, é possível fazer tudo com tudo, você só não vai conseguir justiticar o investimento para fazer isso.

É uma visão.

Voltando ao assunto, quanto ao exterior, depende do tipo de empresa. É muito parecido com o que ocorre aqui. Consultorias ficam com tecnologias mais comerciais para cuidar do be-á-bá do back office, enquanto startups inovam e experimentam mais, normalmente usando OSS, claro.

Trabalhei 2 anos com RoR e te digo os motivos da escolha de RoR para projetos novos:

Velocidade de desenvolvimento("**Gems**" -> coisas do cotidiano já estão prontas, só fazer um "gem install nome\_da\_gem" e era isso);

Código extremamente legível;

Boas praticas(exemplo: migrations, testes, integração continua, DevOps, tudo é muito claro para a comunidade RoR e a maioria dos profissionais não fica sossegado na linguagem, sempre estão buscando aprender coisas novas).

**Convention over configuration(siga a convenção e não se estresse com configurações)**,

Comunidade extremamente unida e participativa são os motivo da escolha de Ruby com Rails.

Diego, sinceramente, acho que não vai mudar, o Asp.Net não vai ser escolhido simplesmente porque atualmente ele é mais demorado para entregar uma aplicação.

A comunidade .Net não está acostumada com o conceito do software livre, colaboração, contribuição e também não tem o costume de fazer coisas e liberar os fontes e isso pesa muito na hora de escolher uma tecnologia.

Imagine o seguinte cenário: Tu quer desenvolver uma aplicação, sabe que nela terá autenticação, autorização, cadastros de usuários e permissões e vai existir o conceito de gamificação e upload de arquivos para o amazon s3. Isso tudo já está pronto, basta você criar o projeto, instalar 4 gems, gerar as views, e pensar na forma como tu quer implementar a gamificação e o upload, porque o grosso do código já está pronto.

Essa é a cultura da comunidade Ruby, ajudar os outros a resolver os problemas que nós já passamos.

Como exemplo, aqui as gems que usariamos para fazer a aplicação:

Autenticação: <https://rubygems.org/gems/devise>

Autorização: <https://rubygems.org/gems/cancancan>

Gamification: <https://rubygems.org/gems/gioco>

Upload: <https://rubygems.org/gems/refile>

O que eu tenho certeza é que cada uma tem o seu espaço e com certeza tem espaço de sobra no mercado para boas tecnologias. A microsoft vem melhorando muito nestes últimos anos(liberando os fontes do Asp.Net, EF, etc...) isso com certeza vai fazer a comunidade .Net olhar com bons olhos o a colaboração, contribuição e o software livre, e com isso, mais e mais ferramentas surgirão para facilitar o dia a dia do desenvolvedor .net.

Fato. Realmente determinados tipos de soluções acabam sendo influenciados bastante pela linguagem escolhida. Mas acaba que coisas novas as vezes depende de toda uma movimentação da industria. Programação funcional por exemplo, acho que vai demorar pra isso ser usado da maneira como usamos orientação a objetos hoje, então pra eu escolher isso pra minha solução, eu tenho que pesar.

"Por exemplo, se o time de uma empresa pequena se sente confortável com Clojure, o custo de adoção é zero se comparado a outras linguagens."  
  
O custo de adoção acaba não se baseando so nisso. Vai se basear também em quando eu for contratar mais programadores ou trocar os que tem na equipe hoje. Vai se basear se amanhã por exemplo eu precisar integrar com objetos COM por exemplo, o quão de suporte Clojure tem pra isso? Então assim, acho que é mais complexo do que parece.

No fim, o que eu acho é que formas diferentes de pensar pra soluções de problemas você acaba adquirindo melhor, se for conhecer mais as APIs do OS ou do Framework em que você trabalha por exemplo... se for conhecer mais conceitos de design de forma mais abstrata, pois assim você acaba sabendo não como uma linguagem funciona, mas como várias linguagens funcionam em cima de um conceito. Por exemplo o conceito que o I/O Completion Ports usa, entender como ele gerência as threads, acaba que NodeJs, SignalR, Socket.IO são só diferentes implementações. Assim acaba que linguagens são só implementações dos mesmos conceitos de forma diferentes. Algoritmos, etc.  
  
Mas enfim... sei la, isso é uma opinião até bem pessoal minha de como tenho lidado com meus problemas, não quer dizer que é "certo", se existisse realmente o "certo". Mas se saber várias linguagens de fato te faz um solucionador de problemas melhor, quem sou eu... Parece que tudo depende em que nível de abstração você ta querendo lidar. Enfim...

Não tenho intenção de citar todos os possíveis custos de adoção de uma linguagem - isso levaria tempo demais e não cabe em uma mensagem de grupo de discussão. Concordo que é complexo.

No cenario de adoção de Clojure, supondo que o time trabalha atualmente com Ruby (porque usar Java como exemplo é facil demais):

1. Contratar bons programadores é extremamente dificil em qualquer cidade grande. Não faz muita diferença se é para trabalhar com Java, C#, COBOL, Ruby ou Clojure.

2. Ja que o time existe se sente confortavel com Clojure, não seria necessário um grande investimento ou "troca" de equipe.

3. Integrar com COM seria tão dificil em Clojure quanto com Ruby, mas convenhamos, um componente COM é extremamente improvavel nesse contexto.

Essa analise parte do principio que o time é formado por bons programadores - não faz sentido uma mudança dessas com um time fraco. Tambem se baseia no fato que o time é maduro, tem interesse na mudança e existe fundamentação na adoção. É um cenário dificil - por isso mudanças assim são dificeis. Eu não acho que você esta errado, mas acho que talvez esteja sendo muito pessimista.

Uma estratégia que tenho utilizado para adoção de novas ferramentes e linguagens é aplica-las primeiro em sistemas pequenos. Isso da ao time a oportunidade de avaliar a experiencia, e o risco é baixo dado que em ultimo caso o sistema pode ser reescrito.
